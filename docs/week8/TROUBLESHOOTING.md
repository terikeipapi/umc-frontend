# 8주차 트러블슈팅 보고서

작성일: 2026년 11월 17일(한국 시간)

대상: UMCine 로그인 전용 라우트와 찜·평점 API 연동

## 1. Route Group으로 묶어도 로그인 제한은 생기지 않음

**발견:** 기존 `/mypage`, `/mypage/edit`는 독립 라우트였고 인증 없이 예시 회원 정보를 표시했다. `(authenticated)` 폴더만 추가하면 파일을 모을 수 있지만 공통 인증 검사와 렌더링 경계가 만들어지는 것은 아니다.

**원인:** Route Group은 URL을 바꾸지 않는 파일 구성 문법이다. URL 경로 없이 부모 로직과 컴포넌트를 공유하려면 별도의 pathless Layout Route가 필요하다. [TanStack Router 공식 문서](https://tanstack.com/router/latest/docs/routing/file-naming-conventions)

**해결:** `(authenticated)/_auth.tsx`에서 `beforeLoad`로 세션을 검사하고 `<Outlet />`으로 자식을 렌더링했다. 마이페이지와 수정 라우트를 `_auth/` 하위로 옮겼다. 생성 파일은 라우터 플러그인으로 재생성한다. 비로그인 이동은 `redirect` 검색 파라미터에 원래 주소를 보관하고 로그인 후 안전한 내부 주소만 허용한다.

**검증:** 직접 주소 접근, 만료·비로그인 세션, 로그인 후 원래 화면 복귀를 라우터와 실제 컴포넌트 테스트로 확인했다. 실제 생성 트리에서 두 페이지가 `_auth`의 자식인지도 확인했다.

## 2. 기존 로그인·북마크는 서버 데이터가 아니었음

**발견:** 로그인 폼은 미리보기 안내만 표시했다. 회원 정보는 `profile-preview-store`, 북마크는 계정 구분 없는 localStorage 배열에 저장됐다. 또한 로컬 `study` 서버에는 요청된 `/favorites` API와 대응 테이블이 없었다.

**원인:** 이전 과제의 화면·브라우저 저장 구현이 남아 있었고 실제 인증 및 찜 서버 계약이 준비되지 않았다. 이 상태에서는 로그인 전용 라우트와 회원별 찜 목록을 구현해도 검증할 수 없다.

**해결:** 로그인·내 정보 API를 연결하고 토큰의 `sub`로 현재 회원 ID를 얻었다. 찜 조회·추가·삭제는 서버 API를 사용하도록 교체했다. 로컬 백엔드에는 JWT 보호 찜 컨트롤러·서비스와 추가형 DB 스크립트를 작성했다. `UNIQUE(member_id,movie_id)`와 원자적 upsert로 동시 추가 중복을 막고 삭제 조건에도 회원 ID를 포함했다. 과거 로컬 북마크는 특정 계정의 소유라고 판단할 근거가 없으므로 자동 이관하지 않는다.

**검증:** 기존 데이터를 유지한 테이블 준비, 인증 없는 요청 거부, 회원별 목록 분리, 동시·반복 추가와 반복 삭제를 백엔드 테스트 및 실제 로컬 HTTP·MySQL 검증으로 확인했다.

## 3. 영화 ID와 평점 ID를 혼동하면 다른 URL로 수정·삭제됨

**발견:** 상세 화면에서 알고 있는 ID는 `movieId`지만 평점 수정·삭제 API의 경로는 `ratingId`를 요구한다. 기존 평점이 있는지도 영화 상세 응답만으로 알 수 없다.

**해결:** `GET /members/{memberId}/ratings` 결과에서 현재 영화의 항목을 찾아 별점·후기를 채운다. 항목이 없을 때만 POST하고, 있으면 응답의 `ratingId`로 PATCH·DELETE한다. 조회 실패 시 새 평점이 없다고 가정하지 않고 재조회 버튼을 제공한다. 별점 범위와 후기 길이는 기존 백엔드 DTO의 1~5 정수·500자 규칙에 맞췄다.

**검증:** `movieId=550`과 서로 다른 `ratingId`를 사용하는 API·DOM 테스트에서 POST → PATCH → DELETE 전 과정을 검증했다. 실제 서버에서도 평점 생성 결과의 ID로 수정·삭제했으며 다른 회원의 수정·삭제는 403으로 거부됐다.

## 4. 로그아웃 후 이전 계정의 응답·캐시가 남을 수 있음

**원인:** 쿼리 키에 회원 구분이 없거나 토큰만 제거하면 개인 데이터 캐시는 남는다. A 계정 요청이 진행 중일 때 B로 로그인하면 뒤늦은 응답이 B의 화면에 잘못 반영될 수도 있다. 이전 토큰의 401이 새 세션을 지우는 경우도 막아야 한다.

**해결:** 회원 ID를 개인 쿼리 키에 넣고 세션 변경 시 해당 쿼리만 취소·제거한다. 보호 API는 요청 당시의 Authorization이 현재 토큰과 같은지 응답 시점에도 확인한다. 이전 세션의 응답은 버리고 현재 세션과 일치하는 요청의 401만 로그아웃 처리한다. 변경 성공 콜백도 토큰을 확인한다. 공용 TMDB 캐시는 유지한다.

**검증:** 회원별 키 분리, 비로그인 시 요청 없음, 지연된 이전 세션의 성공·401 응답, 현재 세션 401 해제를 테스트했다. 열려 있는 보호 페이지의 토큰 만료 시 로그인 이동과 개인 캐시 제거도 DOM 테스트로 확인했다.

## 5. 409 충돌 후 평점 재조회가 작성 중인 입력을 덮어씀

**재현:** 첫 평점 조회는 빈 배열이고 사용자가 3점·후기를 작성한다. 다른 탭에서 먼저 평점을 등록한 상황을 모의 응답으로 만들면 POST가 409를 반환한다. 후속 GET은 서버의 기존 평점을 반환한다.

**원인:** 처음에는 에디터의 React `key`에 서버의 `ratingId`, `score`, `comment`를 포함했다. 오류 후 캐시를 재검증하면서 서버 평점이 달라지면 컴포넌트가 다시 마운트되어 작성 중인 입력이 서버 값으로 교체됐다. 단순 503 뒤 같은 데이터를 받는 테스트에서는 드러나지 않는 문제였다.

**해결:** 에디터는 명시적인 버전으로 식별하고 저장·삭제가 성공했을 때만 버전을 올려 초기화한다. 실패·충돌 후 서버를 재조회할 때는 작성 중인 값은 보존하면서 수정 대상 `ratingId`만 최신 조회 결과를 사용한다. 계정·영화가 바뀌면 별도의 부모 경계가 폼을 초기화한다.

**검증:** 회귀 테스트에서 `GET [] → POST 409 → GET ratingId=91` 뒤에도 작성한 3점·후기가 남는지 확인했다. 이어지는 재시도가 `PATCH /ratings/91`에 작성한 값을 보내는 것까지 통과했다. [평점 충돌 회귀 테스트](../../tests/movie-member-interactions.test.mjs)

## 6. SSR 테스트가 브라우저 세션 화면 대신 로딩 화면을 반환함

**현상:** 첫 전체 테스트에서 65개 중 2개가 실패했다. 프로필 HTML에 이메일이 없고, 수정 화면에서 이메일 레이블을 찾지 못했다. 실제 결과에는 `내 정보를 불러오고 있어요.`라는 로딩 문구가 있었다.

**원인:** 테스트가 서버 렌더링 결과에도 브라우저 세션으로 조회한 회원 정보가 즉시 표시된다고 가정했다. Zustand의 서버 스냅샷과 브라우저의 현재 세션은 구분되므로 해당 SSR 경로는 개인 정보 없이 조회 대기를 표시한다.

**해결:** SSR 검증은 로딩과 개인 정보 비노출을 확인하도록 수정했다. 실제 회원 정보 표시와 수정은 QueryClientProvider가 있는 DOM 환경에서 API 모의 응답을 받아 확인한다. 제품 코드를 테스트 기대값에 맞춰 개인 정보가 서버 HTML에 나타나게 바꾸지 않았다.

**검증:** SSR 검증과 DOM 회원정보 조회·수정·취소 검증을 포함한 최종 전체 테스트 69개가 모두 통과했다.

## 7. 화면 테스트의 검증은 끝났지만 프로세스가 종료되지 않음

**현상:** 찜·평점 DOM 테스트의 모든 assertion은 통과했는데 Node.js 프로세스가 계속 실행됐다.

**원인:** Query mutation의 브라우저용 GC 타이머가 테스트 종료 후에도 남아 있었다.

**해결:** 해당 독립 DOM 테스트의 QueryClient에만 `mutations.gcTime: 0`을 설정하고 마운트·쿼리·테스트 서버를 정리했다. 제품의 캐시 설정은 유지했다.

**검증:** 이후 해당 테스트 명령과 최종 전체 테스트 명령 모두 종료 코드 0으로 정상 종료했다.

## 검증 결과와 한계

프런트엔드 타입 검사·69개 테스트·빌드, 백엔드 단위 테스트 1개·E2E 187개·실제 HTTP/MySQL 검증 33건이 통과했다. 백엔드 린트는 종료 코드 0이며 기존 파일의 타입 경고 2개가 남아 있다.

명령별 결과, [실제 HTTP 기록](https://github.com/terikeipapi/umc-backend/blob/main/output/week8/api-verification.json), 모의 응답과 실제 서버 검증의 구분은 [미션 기록](MISSION.md)에 정리했다. 이번 작업에서 실제 브라우저 시각 검수와 실제 TMDB를 포함한 브라우저 E2E는 수행하지 않았다.
